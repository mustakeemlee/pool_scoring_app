# Self-Hosted Docker Compose Stack, Sub-phase A Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up a separate, production-shaped Docker Compose stack (self-hosted Postgres, GoTrue, PostgREST, Kong, and a containerized frontend build) that runs alongside — not instead of — the existing `supabase start` CLI dev workflow.

**Architecture:** Five containers on one Compose network. `db` (supabase/postgres, migrations from `supabase/migrations/*.sql` mounted straight in) is fronted by `auth` (GoTrue) and `rest` (PostgREST), which `kong` routes to on a single port (8000) using the exact URL shape `supabase-js` already expects. `frontend` is a separate multi-stage build producing a static Vite build served by nginx (port 8080).

**Tech Stack:** Docker Compose, the exact pinned Supabase self-host images already in local use (`supabase/postgres:17.6.1.143`, `supabase/gotrue:v2.192.0`, `supabase/postgrest:v14.14`, `supabase/kong:2.8.1`), Node/Vite/nginx for the frontend.

**Design provenance:** every piece of service wiring in this plan (env vars, the Kong declarative config, the Postgres role-password fixup, the frontend build-context/build-arg approach) was prototyped and verified end-to-end in a real, disposable Docker Compose stack before being written here — including running curl requests through Kong for a REST read, a GoTrue admin user creation, a password sign-in, a service-role insert, and an RLS self-read using the resulting user JWT, plus an actual `docker build` of the frontend image and a live SPA-fallback check. This is not untested boilerplate.

## Global Constraints

- **Separate from daily dev, not a replacement.** Nothing in this plan touches `supabase start`, `supabase/config.toml`, or any file the CLI workflow depends on.
- **Minimal service set.** Only `db`, `auth`, `rest`, `kong`, `frontend`. No Storage, Realtime, imgproxy, analytics/Logflare, Studio, or postgres-meta — this app doesn't use any of them.
- **Edge Functions are out of scope.** The four admin write actions (enter-match, correct-match, close-week, start-season) do not work against this stack yet — that's Sub-phase B. Only public reads and admin login are verified here.
- **Plain HTTP, no reverse proxy or TLS.** Ports exposed directly: Kong on 8000, frontend on 8080.
- **Migrations reused unchanged.** `supabase/migrations/*.sql` is mounted read-only into the `db` container — never copied or duplicated.
- **Frontend build context is the repo root, not `web/`** — `web/src/components/OddsWidget.tsx` imports `../../../src/rating/odds.ts`, reaching outside `web/`.
- **Dev-grade secrets.** `.env.selfhost` (gitignored) holds generated secrets; the compose file and runbook both state plainly these must be rotated before this stack ever runs on a real, internet-facing host.
- **No new automated test suite.** This is infrastructure — verification is docker/curl commands with expected output, run and confirmed at each task, exactly as this plan specifies.

- [ ] **Step 1: Write the secrets generator script**

Create `scripts/generate-selfhost-secrets.mjs`:

```js
// scripts/generate-selfhost-secrets.mjs
//
// Generates dev-grade secrets for the self-hosted docker-compose stack
// (Sub-phase A) and writes them to .env.selfhost (gitignored). Refuses to
// overwrite an existing file, since regenerating would invalidate any
// already-issued GoTrue sessions and the anon/service keys baked into an
// already-built frontend image.
import { randomBytes, createHmac } from 'node:crypto';
import { writeFileSync, existsSync } from 'node:fs';

const outputPath = '.env.selfhost';
if (existsSync(outputPath)) {
  console.error(`${outputPath} already exists -- refusing to overwrite. Delete it first if you want to regenerate.`);
  process.exit(1);
}

function base64url(buf) {
  return buf.toString('base64').replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

function signJwt(payload, secret) {
  const header = { alg: 'HS256', typ: 'JWT' };
  const encodedHeader = base64url(Buffer.from(JSON.stringify(header)));
  const encodedPayload = base64url(Buffer.from(JSON.stringify(payload)));
  const data = `${encodedHeader}.${encodedPayload}`;
  const signature = base64url(createHmac('sha256', secret).update(data).digest());
  return `${data}.${signature}`;
}

const jwtSecret = randomBytes(32).toString('base64');
const postgresPassword = randomBytes(24).toString('base64');
const nowSeconds = Math.floor(Date.now() / 1000);
const expSeconds = nowSeconds + 10 * 365 * 24 * 3600; // 10 years -- dev-grade, rotate before real hosting

const anonKey = signJwt({ role: 'anon', iss: 'pool-league-selfhost', iat: nowSeconds, exp: expSeconds }, jwtSecret);
const serviceRoleKey = signJwt(
  { role: 'service_role', iss: 'pool-league-selfhost', iat: nowSeconds, exp: expSeconds },
  jwtSecret,
);

const content = `# Generated by scripts/generate-selfhost-secrets.mjs -- dev-grade values.
# Rotate ALL of these before ever pointing this stack at a real, internet-facing host.
JWT_SECRET=${jwtSecret}
POSTGRES_PASSWORD=${postgresPassword}
ANON_KEY=${anonKey}
SERVICE_ROLE_KEY=${serviceRoleKey}
`;

writeFileSync(outputPath, content);
console.log(`Wrote ${outputPath}`);
```

- [ ] **Step 5: Write the role-password fixup script**

The `supabase/postgres` image creates the `authenticator`, `supabase_auth_admin`, and `supabase_storage_admin` roles with no password (verified directly against the image's own init scripts), and creates the `auth.uid()`/`auth.role()`/`auth.email()` functions owned by `postgres` rather than `supabase_auth_admin` — both of which need fixing before GoTrue/PostgREST can connect and run their own migrations. Create `docker/db-init/zz-set-role-passwords.sh`:

```sh
#!/bin/sh
set -e
psql -v ON_ERROR_STOP=1 --no-password --no-psqlrc -U supabase_admin -d "$POSTGRES_DB" <<-EOSQL
  ALTER ROLE authenticator WITH PASSWORD '$POSTGRES_PASSWORD';
  ALTER ROLE supabase_auth_admin WITH PASSWORD '$POSTGRES_PASSWORD';
  ALTER ROLE supabase_storage_admin WITH PASSWORD '$POSTGRES_PASSWORD';
  DO \$\$
  DECLARE
    r record;
  BEGIN
    FOR r IN
      SELECT p.oid::regprocedure AS sig
      FROM pg_proc p
      JOIN pg_namespace n ON n.oid = p.pronamespace
      WHERE n.nspname = 'auth'
    LOOP
      EXECUTE format('ALTER FUNCTION %s OWNER TO supabase_auth_admin', r.sig);
    END LOOP;
  END
  \$\$;
EOSQL
```

Make it executable: `chmod +x docker/db-init/zz-set-role-passwords.sh`

The `zz-` prefix is intentional: Postgres's docker-entrypoint runs every top-level `/docker-entrypoint-initdb.d/*.sh` alphabetically, and this must run *after* `migrate.sh` (the supabase/postgres image's own top-level init script, which creates these roles/functions in the first place) — `zz` sorts after `migrate.sh` reliably.

**Files:**

- [ ] **Step 1: Write the nginx SPA-fallback config**

Create `web/nginx.conf`:

```
server {
    listen 80;
    root /usr/share/nginx/html;

    location / {
        try_files $uri /index.html;
    }
}
```

Without this, a direct browser navigation to a client-routed path like `/players/<id>` would 404 — nginx would look for a literal file at that path instead of serving `index.html` and letting React Router handle it. The Vite dev server (used for daily dev via `supabase start` + `npm run dev`) already does this automatically; a plain static nginx server needs it spelled out.

- [ ] **Step 2: Write the multi-stage Dockerfile**

Create `web/Dockerfile`:

```dockerfile
# Build context MUST be the repo root (see docker-compose.yml's frontend
# service: `context: .`) -- web/src/components/OddsWidget.tsx imports
# directly from ../../../src/rating/odds, reaching outside web/ into the
# Phase 1 rating engine.
FROM node:20-alpine AS build
WORKDIR /app
COPY web/package.json web/package-lock.json ./web/
RUN cd web && npm ci
COPY src/rating ./src/rating
COPY web ./web
# Build-time only -- these get compiled into the static JS bundle the same
# way any public client-side config would be, not injected at runtime. This
# is not a secret: the anon key is designed to be safe for a public client
# to hold (RLS is what actually protects data, not key secrecy).
ARG VITE_SUPABASE_URL
ARG VITE_SUPABASE_ANON_KEY
ENV VITE_SUPABASE_URL=$VITE_SUPABASE_URL
ENV VITE_SUPABASE_ANON_KEY=$VITE_SUPABASE_ANON_KEY
RUN cd web && npx tsc -b && npx vite build

FROM nginx:alpine
COPY --from=build /app/web/dist /usr/share/nginx/html
COPY web/nginx.conf /etc/nginx/conf.d/default.conf
```

Note this intentionally runs `npx tsc -b && npx vite build` directly rather than `npm run build` — the `build` npm script also runs `node scripts/generate-env.mjs`, which shells out to `supabase status` (the CLI stack) to discover connection info. That's meaningless inside a Docker build and the wrong target regardless — this stack needs its own Kong URL/anon key baked in, supplied via the `ARG`s above instead. `scripts/generate-env.mjs` itself is untouched, still used for the CLI-based dev workflow.

## Task 4: Self-host seed script and runbook

**Files:**

**Interfaces:**
- Consumes: the full stack from Tasks 1-3 (Kong at `localhost:8000`, `.env.selfhost`'s `ANON_KEY`/`SERVICE_ROLE_KEY`).
- Produces: realistic demo data (a season, players, ratings, matches) visible on every public page, and a documented runbook for bringing the stack up, seeding it, and verifying it — fulfilling the design spec's "Done" criteria.

The existing `scripts/seed.mjs` exercises the real `enter-match`/`close-week` Edge Functions so the resulting ratings are internally consistent with the actual Glicko-2 pipeline — but this stack has no Edge Runtime yet (that's Sub-phase B), so it can't be reused as-is. This new script inserts realistic-*looking* `player_season_ratings`/`matches` rows directly via PostgREST instead. That's an intentional, narrower scope: the goal here is proving the self-hosted Postgres/GoTrue/PostgREST/Kong/frontend wiring works end-to-end with real data flowing through it, not re-proving the rating math — Phase 1's unit tests and Phase 2's Edge Function integration tests already cover that.

- [ ] **Step 1: Write the seed script**

Create `scripts/seed-selfhost.mjs`:

```js
// scripts/seed-selfhost.mjs
//
// Seeds the self-hosted docker-compose stack (Sub-phase A) with realistic
// demo data. Unlike scripts/seed.mjs (which replays the real enter-match/
// close-week Edge Functions), this stack has no Edge Runtime yet -- so this
// script inserts player_season_ratings/matches rows directly via PostgREST.
// It exists to prove the self-hosted wiring works end-to-end with real data,
// not to re-verify the rating math (already covered by Phase 1/2's tests).
//
// Usage: node scripts/seed-selfhost.mjs
// Requires: docker compose --env-file .env.selfhost up -d (see docker/README.md)
import { createClient } from '@supabase/supabase-js';
import { readFileSync } from 'node:fs';

function loadSelfhostEnv() {
  const content = readFileSync('.env.selfhost', 'utf-8');
  const env = {};
  for (const line of content.split('\n')) {
    const match = line.match(/^(\w+)=(.*)$/);
    if (match) env[match[1]] = match[2];
  }
  return env;
}

const API_URL = process.env.SELFHOST_API_URL ?? 'http://localhost:8000';
const env = loadSelfhostEnv();

const FIRST_NAMES = ['Alex', 'Jordan', 'Sam', 'Taylor', 'Morgan', 'Casey', 'Riley', 'Jamie'];
const GRADES = ['A+', 'A', 'B+', 'B', 'C+', 'C', 'D'];

async function main() {
  const serviceClient = createClient(API_URL, env.SERVICE_ROLE_KEY);

  const email = `selfhost-seed-admin-${Date.now()}@example.com`;
  const password = 'selfhost-seed-password-123!';
  const { data: userData, error: createUserError } = await serviceClient.auth.admin.createUser({
    email,
    password,
    email_confirm: true,
  });
  if (createUserError || !userData?.user) {
    throw new Error(`Failed to create seed admin user: ${createUserError?.message ?? 'no user returned'}`);
  }

  const { error: adminInsertError } = await serviceClient
    .from('admin_users')
    .insert({ id: userData.user.id, display_name: 'Selfhost Seed Admin', role: 'admin' });
  if (adminInsertError) {
    throw new Error(`Failed to insert admin_users row: ${adminInsertError.message}`);
  }

  const { data: season, error: seasonError } = await serviceClient
    .from('seasons')
    .insert({ name: 'Selfhost Seed Season', start_date: '2026-01-01', status: 'active' })
    .select('id')
    .single();
  if (seasonError || !season) {
    throw new Error(`Failed to create seed season: ${seasonError?.message ?? 'no season returned'}`);
  }

  const { data: players, error: playersError } = await serviceClient
    .from('players')
    .insert(FIRST_NAMES.map((name) => ({ full_name: `${name} Selfhost` })))
    .select('id');
  if (playersError || !players) {
    throw new Error(`Failed to create seed players: ${playersError?.message ?? 'no players returned'}`);
  }

  const ratingsRows = players.map((player, index) => ({
    player_id: player.id,
    season_id: season.id,
    rating: 1500 + (players.length - index) * 20,
    matches_played: 3,
    is_provisional: false,
    grade: GRADES[index % GRADES.length],
    season_points: (players.length - index) * 10,
  }));
  const { error: ratingsError } = await serviceClient.from('player_season_ratings').insert(ratingsRows);
  if (ratingsError) {
    throw new Error(`Failed to insert player_season_ratings: ${ratingsError.message}`);
  }

  const matchesRows = [];
  for (let i = 0; i < players.length - 1; i += 2) {
    const [a, b] = [players[i].id, players[i + 1].id];
    matchesRows.push({
      season_id: season.id,
      match_date: '2026-01-08',
      player_a_id: a,
      player_b_id: b,
      frames_a: 5,
      frames_b: 2,
      winner_id: a,
      entered_by: userData.user.id,
    });
  }
  const { error: matchesError } = await serviceClient.from('matches').insert(matchesRows);
  if (matchesError) {
    throw new Error(`Failed to insert matches: ${matchesError.message}`);
  }

  console.log(`Seeded season ${season.id} with ${players.length} players and ${matchesRows.length} matches.`);
  console.log(`Admin login: ${email} / ${password}`);
}

main().catch((error) => {
  console.error('Selfhost seed script failed:', error);
  process.exit(1);
});
```
